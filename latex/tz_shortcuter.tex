\section{Назначение и цели создания системы}

\subsection{Назначение системы}

\systemname{} представляет собой веб-приложение для сокращения длинных URL-адресов. Система предоставляет пользователю короткую ссылку вида \texttt{http://<host>/<code>}, переход по которой перенаправляет браузер на исходный URL.

Система позволяет:

\begin{itemize}
	\item генерировать короткие ссылки из длинных URL-адресов;
	\item управлять своими ссылками (просмотр списка, удаление);
	\item настраивать пользовательские алиасы (осмысленный короткий код вместо автоматически сгенерированного);
	\item блокировать нарушителей средствами административной панели.
\end{itemize}

Система предусматривает разграничение доступа по трём группам пользователей: гость, пользователь, администратор.

\subsection{Цели создания системы}

Основными целями разработки \systemname{} являются:

\begin{enumerate}
	\item создание простого и предсказуемого инструмента сокращения URL-адресов;
	\item разграничение доступа по группам пользователей;
	\item обеспечение воспроизводимого развёртывания и автоматизированной доставки приложения (конвейер CI/CD);
	\item подготовка базы для дальнейшего расширения функциональности.
\end{enumerate}

% 3. Характеристика объектов автоматизации
\section{Характеристика объектов автоматизации}

\subsection{Описание объекта автоматизации}

Объектом автоматизации является процесс преобразования длинных URL-адресов в короткие и последующего перенаправления по ним. Система автоматизирует:

\begin{itemize}
	\item генерацию уникального короткого кода для исходного URL;
	\item хранение соответствия «код -- исходный URL» в базе данных;
	\item перенаправление браузера по короткой ссылке (HTTP 301);
	\item ведение списка ссылок пользователя и проверку прав доступа к ним.
\end{itemize}

\subsection{Группы пользователей}

В системе выделяются три группы пользователей. Каждый участник команды реализует функциональность одной группы.

% 4. Требования к системе
\section{Требования к системе}

\subsection{Требования к системе в целом}

\subsubsection{Требования к функциональности}

Система должна обеспечивать:

\begin{enumerate}
	\item создание короткой ссылки из произвольного URL без регистрации (гость);
	\item автоматическую генерацию уникального короткого кода;
	\item переход по короткой ссылке с перенаправлением на исходный URL (код ответа 301);
	\item задание пользовательского алиаса вместо автоматически сгенерированного кода;
	\item просмотр списка собственных ссылок зарегистрированным пользователем;
	\item удаление собственной ссылки зарегистрированным пользователем;
	\item регистрацию и вход по паре «email -- пароль»;
	\item административное управление пользователями (просмотр, блокировка, разблокировка).
\end{enumerate}

\subsubsection{Требования к программному интерфейсу}

\subsubsection{Требования к обработке исключительных ситуаций}

Система должна предусматривать обработчики пользовательских исключительных ситуаций (хуки), возвращающие клиенту единый формат ответа:

\begin{itemize}
	\item \texttt{400} -- некорректный или недостижимый исходный URL, недопустимый алиас;
	\item \texttt{403} -- попытка доступа к чужой ссылке, действие заблокированного пользователя;
	\item \texttt{404} -- переход по несуществующему короткому коду;
	\item \texttt{409} -- алиас уже занят;
	\item \texttt{500} -- внутренняя ошибка сервера с записью в журнал.
\end{itemize}

Обработка выполняется на уровне приложения (не только средствами веб-сервера) и сопровождается понятным сообщением для пользователя.

\subsubsection{Требования к надёжности}

Система должна:

\begin{itemize}
	\item сохранять согласованность данных при сбоях;
	\item предусматривать резервное копирование базы данных перед изменением схемы;
	\item корректно обрабатывать недоступность базы данных.
\end{itemize}

\subsubsection{Требования к безопасности}

\begin{itemize}
	\item аутентификация по паре «email -- пароль» с хранением пароля только в виде хеша;
	\item проверка прав доступа на уровне сервера: пользователь работает только со своими ссылками;
	\item валидация всех входных данных;
	\item отсутствие учётных данных и секретов в репозитории проекта.
\end{itemize}

\subsection{Требования к видам обеспечения}

\subsubsection{Требования к информационному обеспечению}

Хранение данных осуществляется в реляционной базе данных. Структура базы должна содержать не менее двух таблиц:

\begin{itemize}
	\item \texttt{users} -- учётные записи (email, хеш пароля, роль, признак блокировки, дата регистрации);
	\item \texttt{links} -- ссылки (короткий код, исходный URL, ссылка на владельца, дата создания).
\end{itemize}

Короткий код должен быть уникальным. Все изменения схемы базы данных выполняются миграциями, хранимыми в репозитории проекта.

\subsubsection{Требования к программному обеспечению}

\begin{itemize}
	\item Серверная часть: язык Python 3.11+, фреймворк Flask;
	\item База данных: PostgreSQL 14+;
	\item Контейнеризация: Docker, Docker Compose;
	\item Клиентская часть: любой современный браузер (Chrome, Firefox, Edge);
	\item Инструменты сборки и доставки: TeamCity, Docker Hub, Git.
\end{itemize}

\subsubsection{Требования к техническому обеспечению}

Система развёртывается в контейнерах на учебных стендах \texttt{test}, \texttt{stage} и \texttt{prod}, каждый из которых представлен отдельной виртуальной машиной с Unix-подобной операционной системой. Минимальные требования на один стенд: 1 ядро, 1 ГБ оперативной памяти, 10 ГБ дискового пространства.
