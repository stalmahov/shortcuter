## Требования и выбор инструментов

Задание: методичка ЛР6, стр. 3, пункты 1–4. Исследовать анализаторы для стека проекта, выбрать минимум два вида, встроить блокирующие проверки в TeamCity, подготовить текст и скриншоты.

| Средство | Вид и область | Решение |
|---|---|---|
| Bandit | Безопасность Python по AST | Выбран для app; не требует запуска приложения, PostgreSQL или аккаунта |
| Gitleaks | Секреты в файлах разных языков | Выбран; дополнен правилами паролей с низкой энтропией и fallback JWT |
| Semgrep | Анализ Python и JavaScript по правилам | Альтернатива с более широкой областью; для минимального решения выбран Bandit |
| Ruff / ESLint | Качество Python / JavaScript | Другой допустимый вид, но не заменяет анализ безопасности и поиск секретов |

Bandit 1.8.6 имеет LOW/MEDIUM/HIGH, поэтому HIGH принят как максимальный уровень по условию задания. CRITICAL этому инструменту не присваивается. Остаётся риск буквальной трактовки преподавателем слова CRITICAL; шкала и решение должны быть явно указаны на защите. Все находки сохраняются, HIGH и ошибки анализа останавливают шаг. Gitleaks 8.30.0 останавливает шаг при любой найденной записи. Ошибки инструмента также не превращаются в успех.

Gitleaks не доказывает отсутствие всех возможных секретов. Пользовательские правила покрывают присваивания password/JWT_SECRET/POSTGRES_PASSWORD, .env и Python fallback JWT. Шаблоны и находки необходимо разбирать; весь app или config не исключается. Из результатов исключены генерируемые reports, .git и установленные зависимости.

Источники: https://bandit.readthedocs.io/en/latest/man/bandit.html ; https://github.com/gitleaks/gitleaks ; https://semgrep.dev/docs/ ; https://docs.astral.sh/ruff/ ; https://eslint.org/docs/latest/ . Сравнение документальное; альтернативные анализаторы не запускались.

## Минимальный план

1. Подготовить скрипты и конфигурацию в отдельной ветке.
2. Проверить синтаксис, реальные исходники и положительные/отрицательные примеры без приложения и БД.
3. После разрешения push опубликовать ветку. Не активировать скрипты на ветках, где файлов ещё нет.
4. Добавить два Command Line шага и правило артефактов; пока ветка не опубликована, держать новые шаги отключёнными.
5. Проверить только новые шаги в конфигурации без push/deploy. Общий полный прогон — только по отдельному разрешению.
6. Зафиксировать реальные настройки, ошибку и успех. Сверить пункты методички.

## Локальные команды

Использовать Python 3.11. Bandit 1.8.6 несовместим с Python 3.14: эксперимент это подтвердил; ошибка не была засчитана как успех.

```bash
python3.11 -m venv .venv
. .venv/bin/activate
python -m pip install -r ci/requirements-static.txt
# Gitleaks 8.30.0 установить из официального release под ОС и архитектуру.
bash ci/bandit.sh
bash ci/gitleaks.sh
python ci/verify-static.py
```

На агенте с Docker вместо установки Python и Gitleaks:

```bash
bash ci/container-scan.sh bandit
bash ci/container-scan.sh gitleaks
```

Контейнерный вариант передаёт файлы через tar/stdin: не зависит от совпадения checkout-пути внутри агента и на хосте Docker. Приложение и БД не запускаются. Образ Python фиксирует minor 3.11, но не digest; Gitleaks фиксирует версию. Контейнерный вариант проверен на агенте TeamCity в сборках 141 и 142; локальный Docker не использовался.

## TeamCity

В доступной Safari-сессии подтверждён проект Shortcuter, конфигурация Shortcuter_Build. Сейчас есть четыре шага: build, tests, push, deploy stage. После восстановления обычного окна Safari сохранены шаги lab6_bandit и lab6_gitleaks, оба отключены по согласованию с пользователем. Порядок: Bandit, Gitleaks, build, tests, push, deploy stage. Сохранено правило reports/static/** => static-analysis; публикация Even if build fails. В Failure Conditions подтверждён включённый флажок отказа по ненулевому коду. Сборки не запускались. Сервер показывает две критические ошибки: конфликт классов XMLGrammarPool и запрет clean-up вследствие ошибки конфигурации. Их исправление не входит в ЛР6; нельзя считать их причиной отказа сканеров без проверки.

После публикации файлов:

1. Build → Settings → Build Steps → Add build step → Command Line.
2. Имя Lab6 Bandit, ID lab6_bandit, Custom script: `bash ci/container-scan.sh bandit`.
3. Второй шаг: Lab6 Gitleaks, ID lab6_gitleaks, Custom script: `bash ci/container-scan.sh gitleaks`.
4. До готовности ветки отключить оба шага через меню шага Disable. Не нажимать Run общего Build.
5. Через Reorder поставить новые шаги перед build. Условия по именам веток не добавлять. Последующие шаги должны выполняться только при успехе предыдущих.
6. General → Artifact paths: ДОБАВИТЬ строку `reports/static/** => static-analysis`, сохранив существующие правила. Publish artifacts: Even if build fails.
7. Failure Conditions: убедиться, что ненулевой exit code шага делает сборку неуспешной. Проверить фильтр веток VCS/Trigger, чтобы анализ действительно выполнялся во всех нужных ветках.
8. Для проверки только анализаторов использовать отдельную конфигурацию без триггера, push, deploy и тестов с БД либо доступный выбор отдельных шагов. Не отключать чужие шаги общего Build ради эксперимента.

## Фактические результаты

- Bash syntax: успешно для ci/*.sh.
- git diff --check: успешно.
- Bandit на app: exit 0, 0 находок, 0 ошибок.
- Gitleaks после исправления: exit 0, находок нет. Удалён fallback JWT, поля секретов в .env.example пустые, пароль в DATABASE_URL подставляется Docker Compose. До исправления были три находки; их значения не публиковались.
- Два чистых примера: оба сканера exit 0.
- Небезопасный subprocess с shell=True: Bandit exit 1.
- Вымышленный пароль в изолированном fixture.env: Gitleaks exit 1.
- Четыре проверки выполняются ci/verify-static.py в временных каталогах. Это локальные контрольные примеры, НЕ сборки TeamCity.
- Реальные результаты находятся в reports/static/*.json и *.log. Каталог исключён из Git.

JWT_SECRET теперь обязателен: отсутствие, пустая строка и пробелы останавливают запуск с понятной ошибкой. Четыре точечные проверки конфигурации прошли (reports/static/config-proof.json). Тесты получают временный ключ через secrets.token_hex(32), данные БД не затрагивались. Перед merge необходимо дополнить существующий deploy шаг передачей JWT_SECRET: сейчас в нём указан SECRET_KEY. Это отдельное изменение общего шага, пока НЕ выполнено. При использовании собственного уже заполненного .env значения не меняются. Новую копию .env.example нужно заполнить перед запуском.
