# Миграции PostgreSQL

`services/db/schema.sql` загружается при первой инициализации PostgreSQL в Docker.
Для существующей базы изменения применяются через Alembic. Перед миграцией
сохраните копию через `ci/db-backup.sh` в каталог с ограниченным доступом. Для копии используйте клиентские утилиты
той же основной версии, что и сервер PostgreSQL.

Установите зависимости мигратора и укажите профиль libpq `PGSERVICE` или
строку подключения `DATABASE_URL` из окружения стенда.

```sh
python -m pip install -r requirements.txt -r requirements-migrations.txt
python -m alembic upgrade head
python -m alembic current
```

Ревизия `000` создаёт исходные таблицы на пустой базе. На существующей базе
она сохраняет таблицы и данные. `001` добавляет заголовок ссылки, а `002`
добавляет дату блокировки пользователя. Обе ревизии применяют SQL-файлы
из этого каталога. На стенде с ручной `001` колонка уже есть, её значения
сохраняются. Для пользователей, заблокированных до `002`, дата остаётся
пустой до новой блокировки.

После миграции можно сравнить публичную схему с контрольным стендом через
`ci/db-schema-compare.sh`. Alembic хранит ревизии в схеме
`shortcuter_migrations`. Учётной записи мигратора нужны права на изменение
таблиц и создание этой схемы. Рабочий volume PostgreSQL сохраняется.
При откате приложения дополнительные колонки могут оставаться в БД.
Для отката данных используйте проверенную резервную копию.

На TEST сначала примените миграцию и запустите тесты проекта. В шаге
TeamCity для STAGE выполните сверку с TEST и миграцию.

```sh
bash ci/db-migrate.sh test stage
```

В отдельной конфигурации для PROD сначала сделайте резервную копию
и только после успешного завершения этого шага запустите миграцию.
Профили `test`, `stage` и `prod` настраиваются на агенте через libpq.

```sh
PGSERVICE=prod bash ci/db-backup.sh "$BACKUP_DIR"
bash ci/db-migrate.sh stage prod
```

Обновляйте приложение после успешной проверки схемы. Версия приложения
с административной панелью использует поле `users.blocked_at`.
